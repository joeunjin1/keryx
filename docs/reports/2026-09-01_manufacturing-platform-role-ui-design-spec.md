# KERYX 제조실행 플랫폼 역할별 UI 디자인 명세

**작성일:** 2026-08-31 GMT+9  
**적용 범위:** 승인 바이어 신상품·샘플 구독, 제조 프로젝트, 운영 콘솔, 공장 프로젝트 실행, QC 및 출하 업데이트  
**상태:** 구현 기준 확정 — 기존 IP·스토어·B2B 데이터는 보존

## 1. 디자인 결론

KERYX의 역할별 화면은 같은 기능을 단순히 색상만 바꾼 대시보드가 아니라, 각 사용자가 당장 내려야 하는 **한 가지 다음 행동**을 가장 먼저 보이게 해야 한다. 바이어는 제품 기획을 접수하고 승인해야 하며, 운영자는 병목을 해소하고 책임자를 배정해야 하고, 공장은 자기에게 배정된 사양·증빙만 확인해야 한다. QC 및 물류 담당자는 현장 증거와 출하 서류를 남겨야 한다.

공개 IP·스토어·샘플 구독은 첫 접점으로 유지한다. 로그인 후의 제조실행 화면은 공개 쇼핑몰의 연장이 아니라, 고객이 신뢰할 수 있는 **프로젝트 진행실**로 분리한다. 내부 원가·마진·공장 경쟁 정보는 어떤 바이어·공장 화면에도 노출하지 않는다.

## 2. 공통 UI 원칙

| 원칙 | 구현 기준 | 사용자 효과 |
|---|---|---|
| 한 화면, 한 핵심 행동 | 페이지 상단 우측 또는 모바일 하단에 핵심 행동 하나를 고정한다. | 무엇을 해야 하는지 즉시 안다. |
| 단계는 눈에 보이게 | `접수 → 기획 → 매칭 → 샘플 → 승인 → 양산 → QC → 출하 → 완료`를 상태 배지와 진행선으로 표시한다. | 긴 제조 과정의 현재 위치를 이해한다. |
| 역할별 정보 격리 | 바이어 금액은 견적 스냅샷만, 공장에는 배정된 사양만, 내부에는 원가·마진을 별도 카드로 표시한다. | 비용·고객·공장 정보의 교차 노출을 막는다. |
| 모바일 우선 | 기본 1열, `sm` 2열, `lg` 이상에서만 좌측 목록+우측 상세 또는 3열로 확장한다. | 공장·출장 바이어의 휴대폰 사용성을 확보한다. |
| 신뢰 가능한 상태 | 저장·제출·승인 버튼은 처리 중 상태와 성공·실패 안내를 즉시 표시한다. | 반복 클릭과 불안감을 막는다. |
| 문서·이미지 최소 노출 | 목록에서는 썸네일과 파일 종류만, 상세에서만 단기 서명 URL로 미리보기·다운로드를 제공한다. | 로딩 성능과 자료 보안을 함께 지킨다. |
| 언어 일관성 | 모든 버튼, 상태, 빈 화면, 오류, 입력 도움말을 한국어·중국어로 제공한다. | 바이어와 공장 운영을 한 흐름으로 연결한다. |

## 3. 공용 컴포넌트와 디자인 토큰

공통 셸은 `MobileLayout`을 유지하되, 정적 인라인 스타일과 문자 이모지를 점진적으로 제거한다. 메뉴는 `src/config/navigation.ts`만을 단일 원본으로 사용하고, 각 역할 레이아웃은 기존처럼 하나의 셸만 상속한다. `portalType`은 역할별 색상 토큰을 선택하는 데만 사용하며, 접근 권한은 미들웨어·서버 API·RLS에서 각각 강제한다.

| 컴포넌트 | 용도 | 필수 상태 |
|---|---|---|
| `ProjectStageRail` | 프로젝트 전 단계와 현재 병목 표시 | 정상, 주의, 승인 대기, 완료 |
| `ProjectActionBar` | 화면별 핵심 행동을 모바일 하단·PC 상단 우측에 배치 | 기본, 처리 중, 성공, 오류, 비활성 |
| `EvidenceCard` | 샘플·QC·출하 파일의 썸네일·작성자·시각·승인 상태 | 로딩, 비어 있음, 서명 URL 오류 |
| `ApprovalCard` | 바이어 확인 요청, 기준, 첨부 스냅샷, 승인·보완·반려 행동 | 대기, 승인, 보완, 반려, 만료 |
| `ActivityTimeline` | 상태 변경·담당자 배정·승인·파일 등록의 불변 이력 | 최신, 필터, 비어 있음 |
| `RoleEmptyState` | 데이터가 없을 때 역할별 첫 행동을 안내 | 아이콘, 설명, 단일 CTA |

색상은 공개 사이트의 KERYX 브랜드 톤을 유지하고, 상태 색상은 의미를 고정한다. 진행은 중립·청록, 승인 대기는 호박, 위험·반려는 적색, 완료는 녹색을 사용한다. 색상 hex·임의 픽셀 값은 신규 TSX에 직접 작성하지 않고 Tailwind 의미 토큰과 CSS 변수를 사용한다.

## 4. 바이어 UI 설계

### 4.1 `/buyer/discover` — 최근 신상품·샘플 피드

이 페이지의 목적은 구매를 강요하는 것이 아니라, 승인 바이어가 검토 가능한 최근 신상품·샘플을 빠르게 찾고 제조 프로젝트로 전환하도록 하는 것이다. 상단에는 회사 인증·구독 활성 상태를 작게 표시하고, 그 아래에는 **최근 14일 이내**라는 기간 규칙을 설명하는 신뢰 배지를 둔다. 카드에는 신상품명, 상품군, 제공 가능한 샘플, 게시일, 관심 저장만 표시하고 공장명·공장 단가·담당자 연락처는 표시하지 않는다.

모바일에서는 한 줄 필터와 1열 카드, 하단의 `새 제품 요청` CTA를 사용한다. 데스크톱에서는 좌측 필터, 2~3열 카드, 우측의 신규 제조 프로젝트 바로가기 블록으로 확장한다. 만료된 항목은 피드에서 제거하되 관심 저장·프로젝트로 연결된 기록은 바이어의 개인 이력에 유지한다.

### 4.2 `/buyer/projects` — 내 제조 프로젝트

상단은 ‘현재 멈춘 일’을 우선 노출한다. 첫 줄에는 `승인 대기`, `보완 필요`, `진행 중`, `완료` 상태 탭을 두고, 카드에는 프로젝트명·제품군·현재 단계·다음 행동·최근 업데이트만 표시한다. 카드 전체를 누르면 프로젝트룸으로 이동하며, 개별 카드에 여러 보조 버튼을 두지 않는다.

빈 화면은 ‘첫 제품 기획을 접수하면 담당자가 검토해 다음 단계를 안내한다’는 설명과 `제품 요청 시작` 단일 CTA를 표시한다. 신규 프로젝트 CTA는 모바일 하단 고정, 데스크톱 상단 우측 고정으로 배치한다.

### 4.3 `/buyer/projects/new` — 제품 요청 작성

폼은 한 화면에 모든 세부 항목을 강요하지 않는다. `기본 기획`, `수량·희망 일정`, `참고 자료`, `최종 검토`의 네 단계로 나누고 각 단계의 완료 여부를 표시한다. 필수 입력은 제품명, 상품군, 핵심 요구사항이며, 예상 수량·목표 일정은 선택값으로 안내한다. 참고 이미지는 목록에서 압축 미리보기만 보이고 원본은 프로젝트 비공개 영역에 보관한다.

마지막 단계에서만 `초안 저장`과 `접수 제출`을 구분한다. 접수 제출 뒤에는 바이어가 사양을 임의로 바꾸지 않고 보완 요청을 통해 수정하도록 안내한다. 이는 공장·운영자가 서로 다른 사양을 보고 진행하는 문제를 막는다.

### 4.4 `/buyer/projects/[projectId]` — 프로젝트룸

모바일 기본 화면은 다음 행동을 최상단에 둔다. 예를 들어 바이어 승인이 필요할 때는 `승인 요청` 카드와 확인·보완·반려 버튼을 가장 위에 표시한다. 그 아래에는 진행선, 최신 업데이트, 바이어 공개 견적, 샘플 카드, 파일, 이력 순서를 사용한다. 데스크톱에서는 좌측 2/3를 프로젝트 타임라인과 상세, 우측 1/3을 고정된 다음 행동·담당자 안내·승인 목록으로 구성한다.

견적은 운영자가 발행한 바이어 공개 스냅샷만 표시하며, 새 견적이 발행되면 이전 견적은 ‘이전 버전’으로 보관한다. 승인 버튼은 장문 폼 없이 선택+의견 입력으로 끝나야 하며, 입력 직후 처리 상태가 보이도록 한다.

## 5. 운영자·MD UI 설계

### 5.1 `/admin/manufacturing-projects` — 제조 프로젝트 콘솔

운영자 콘솔은 현황 통계보다 병목 해결이 우선이다. 상단에는 `접수 대기`, `바이어 승인 대기`, `QC 증빙 대기`, `출하 문서 대기` 등 행동 가능한 필터를 제공한다. 본문은 모바일에서는 필터 → 프로젝트 카드 → 선택 프로젝트의 상세 순서, 데스크톱에서는 좌측 대기열과 우측 상세 작업 패널의 2열 구조를 사용한다.

우측 상세 패널에는 담당 MD 배정, 단계 전환, 샘플 회차, 공개 견적 발행, 바이어 승인 요청을 순서대로 둔다. 내부 원가·마진·공장 후보 경쟁 비교는 일반 운영 화면이 아닌 `super_admin`/권한 검증이 통과된 별도 비용 검토 화면에서만 사용한다. 모든 변경은 성공 메시지와 함께 운영 이력에 기록한다.

### 5.2 `/admin/buyer-verifications` — 바이어 회사 인증

목록 기본값은 마스킹이다. 회사명, 사업자 번호, 담당자 연락처, 등록증 원문은 불필요하게 함께 보이지 않으며, 상세 열람은 사유를 남기는 별도 행동으로 분리한다. 처리자는 승인·보완 요청·반려·구독 해제를 한 화면에서 결정할 수 있고, 결정 사유와 시각은 수정 불가 이력으로 보여야 한다.

### 5.3 `/admin/new-product-feed` — 신상품·샘플 피드 운영

공장 제출과 내부 등록을 같은 큐에서 관리하되 출처 배지로 구분한다. 카드에는 공개 전 필수 점검표를 둔다. 한국어/중국어 제목, 바이어용 요약, 상품군, 샘플 가능 여부, 비공개 미디어, 게시 기간이 모두 채워져야 `게시` 행동이 활성화된다. 게시 뒤 14일 경과는 삭제가 아닌 `만료` 상태로 이력에 남는다.

## 6. 공장·QC·물류 UI 설계

### 6.1 `/factory/new-product-feed` — 신상품·샘플 제출

기존 공장 제출 화면은 유지하되, 입력 항목을 바이어 공개 정보와 내부 운영 정보로 분리한다. 공장명·연락처·단가·생산 조건은 바이어 피드에 절대 전달되지 않는다는 안내를 제출 버튼 가까이에 둔다. 제출 내역에서는 `검토 요청`, `보완 요청`, `게시 승인`, `기간 종료` 상태와 운영자 보완 사유를 명확히 표시한다.

### 6.2 신규 `/factory/projects` — 배정 제조 프로젝트

공장 화면에는 본인 공장에 배정된 프로젝트만 보인다. 카드에는 제품명, 현재 공장 작업 단계, 납기 기준일, 필요한 제출물만 보이고 바이어 회사명·타 공장 후보·바이어 견적·내부 마진은 보이지 않는다. 상세 페이지에서는 확정된 사양, 골든샘플 기준, 작업 파일, QC 보완 요청, 출하 준비 상태를 탭이 아닌 세로 작업 목록으로 보여 준다.

### 6.3 신규 `/inspector/projects/[projectId]` — 현장 QC 캡처

QC는 현장 휴대폰 사용을 기준으로 한다. 상단에는 프로젝트·상품명·검수 회차만, 본문에는 검사 항목별 합격/보완/불합격, 수량, 사진·동영상·메모를 둔다. 촬영과 저장은 항목마다 즉시 진행하며 네트워크 오류 시 재시도 상태를 보여 준다. 최종 확정은 모든 필수 항목과 증빙이 채워진 경우에만 가능하다.

### 6.4 신규 `/admin/manufacturing-projects/[projectId]/shipment` — 출하 준비

출하 화면은 물류 진행 카드와 서류 목록으로 구성한다. BL, CO, 내륙운송비·해운비, 내륙운임, 해운비 인보이스는 각각 별도 증빙 카드로 관리한다. 각 문서는 `미제출`, `검토 대기`, `승인`, `보완 요청` 상태를 가지며, 최종 승인 이후에만 바이어 프로젝트룸에서 미리보기·다운로드된다. 출하 상태는 단순한 텍스트가 아니라 준비→서류 검토→바이어 공개→출하 완료의 진행선으로 표시한다.

## 7. 구현 우선순위

| 순서 | 디자인·개발 단위 | 완료 기준 |
|---|---|---|
| UI-1 | 공용 `ProjectStageRail`, `ProjectActionBar`, 상태 배지, 빈 화면, 오류·스켈레톤 | 바이어·운영자 제조 프로젝트 화면에서 같은 상태 표현을 사용한다. |
| UI-2 | 바이어 프로젝트 목록·신규 요청·프로젝트룸 재배치 | 모바일에서 핵심 행동이 하단에 고정되고, PC에서 상세·다음 행동이 분리된다. |
| UI-3 | 운영자 제조 콘솔의 병목 큐·담당자·견적·승인 카드 정리 | 한 화면에서 담당자 배정·상태 전환·샘플·견적·승인 요청이 가능하다. |
| UI-4 | 공장 프로젝트 실행·QC 증빙·출하 문서 화면 | 공장은 자기 작업만, 바이어는 승인된 문서만 열람한다. |
| UI-5 | 공용 포털 셸의 아이콘·토큰·모바일 드로어 정리 | 이모지 제거, 최소 터치 영역, 메뉴·언어·활성 상태가 역할별로 일관된다. |

## 8. 검증 기준

모든 신규 화면은 375px, 768px, 1280px 기준에서 확인한다. 비로그인, 바이어, 공장, MD, 관리자 계정별로 페이지와 API가 서로 격리되는지 검증하며, 메뉴에 추가하는 주소는 페이지와 서버 API가 먼저 준비된 경우에만 노출한다. 실제 회사 정보·사업자등록증·상품·견적·QC 증빙은 테스트용으로 임의 생성하지 않는다.

Production 반영 전에는 TypeScript 검사, Next.js 빌드, 공백·경로 검사, Preview 경로 점검을 수행한다. SQL, RLS, 스토리지 버킷, Cron, 외부 API 또는 사이트맵이 바뀌면 변경 내용·영향 범위·검증 결과를 운영 보고서에 누적한다.
